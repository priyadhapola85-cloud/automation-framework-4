Stack and architecture

The project folder already held a Playwright UI-test suite and an unrelated Next.js app (qa-agent). Neither targets this API, so both were left untouched. The framework is a self-contained folder, api-qa-framework/, written in Node.js using:

  • Built-in fetch for HTTP.
  • The built-in http module for the dashboard server.
  • Server-Sent Events for live updates.
  • node:test for unit tests.
  • Two third-party packages for the database: mysql2 (MariaDB driver) and ssh2 (SSH tunnel). These are the same packages the user's earlier, already-configured project uses to reach this database.

The code is CommonJS, like the existing project.

Discovery (Swagger + MariaDB schema)→Catalog (57 cases)→Human review / approval→Run preparation (fresh discovery)→Execution + retries→Classification + defects→Dashboard / report
  • src/discovery.js: discovers the Swagger/OpenAPI contract, the service metadata, and the MariaDB schema (from information_schema).
  • src/db.js: read-only MariaDB access through an SSH tunnel. Every query goes through the shared rate limiter.
  • src/catalog.js: every test case, with its metadata, evidence, assertion logic, and either a run() function (executable) or an observe() function (Needs Validation).
  • src/context.js: a per-attempt context that records HTTP evidence, SQL evidence, assertions, generated inputs and the current stage.
  • src/engine.js: run orchestration, retries, stop, final status and defect analysis.
  • src/rateLimiter.js: one shared limiter for every HTTP request and every DB query. src/httpClient.js: GET-only client with redaction and masking.
  • src/store.js: approvals and run records as JSON files under data/ (git-ignored). src/server.js: the dashboard plus its JSON and SSE API, listening on 127.0.0.1.

7.1 API discovery

The two endpoints are the ones specified in the task. Expected behaviour comes from the API's Swagger documentation: the Swagger UI at /docs, ReDoc at /redoc, and the OpenAPI 3.1 contract at /openapi.json. Each endpoint was also inspected with real requests: the default call, every documented parameter, boundary and invalid values, and existing and non-existing IDs.

At runtime, discoverAll() fetches /openapi.json and / through the shared limiter, with up to 3 retries for 5xx and network errors. For both endpoints it extracts:

  • parameters, with their types, enums, minimum/maximum and defaults;
  • declared response codes and schemas;
  • any security requirement.

The dashboard's API Information panel is rendered from this result. Run preparation repeats discovery, so every run uses the contract as it is at that moment.

Supported parameters come only from the contract: skip, limit, status, tier and city for the collection, and streamer_id for the detail endpoint. Boundary and enum values are read from the live contract at run time. Error behaviour is asserted only where the contract or docs state it: 422 for validation errors and 404 for an unknown ID. Undocumented behaviour is tracked as Needs Validation.

7.2 Database discovery

Access: the user had already configured database access in C:\Users\usre\automation test\.env for an earlier framework. This framework's .env contains only DB_ENV_FILE, which points to that file. Only the DB_* and SSH_* keys are read from it. MariaDB port 3306 is not reachable from outside the server, so src/db.js opens an SSH session to the API host and forwards a stream to the database. Credentials are never logged, shown, or copied into another file.

Discovery queries (read-only, rate-limited) against information_schema:

  • VERSION() and DATABASE(): server version and database name.
  • TABLES: every table.
  • COLUMNS: name, full type (including ENUM values), nullability, key flag and default.
  • KEY_COLUMN_USAGE joined with TABLE_CONSTRAINTS: PRIMARY KEY, UNIQUE and FOREIGN KEY constraints, with referenced table and column.
  • CHECK_CONSTRAINTS: CHECK constraints.
  • One SELECT COUNT(*) per data table.

Relationships come from the declared foreign keys (streamers.location_id → locations.id and earnings.streamer_id → streamers.id), not from naming guesses.

Sensitive data: the users table holds password_hash and api_token. Its rows are never read; only its column names are listed.

Records for validation are read fresh in each run, and again on every retry: streamers, locations, earnings, and the full streamer history in audit_log.

7.4 Real data versus mock or synthetic data

  • Real API, real database. Every check runs against the live API (GET only) and the live MariaDB database (SELECT only). There are no mock APIs, mocked responses, fake databases or simulated runs in the dashboard path.
  • Business records are never fabricated. Existing IDs, cities, tiers, statuses and relationships come from database rows at run time.
  • Generated inputs (disclosed) are used for negative and boundary tests. Each is recorded in the attempt evidence as "Generated input — not a business record". They are:
    • limit = 0, 101, abc, 1.5;
    • skip = -1, abc;
    • invalid enum values;
    • a city string of the form QA-NoMatch-<runId>, checked against every locations row;
    • IDs proven absent: 99999999, qa-not-an-id, a leading-zero variant, a 1024-character string, and ' OR '1'='1. Each is proven absent by SELECT COUNT(*) FROM streamers WHERE id = ? returning 0;
    • an invalid token header in one observation.
  • Unit tests (test/framework.test.js) cover the framework's own logic using a local in-process HTTP server and fixture rows. These fixtures are synthetic. They never reach the dashboard and never stand in for results of testing the real API or database.

7.5 How expected results were established

A case is executable only when the Swagger contract, its documentation text, or the database schema or data establishes the expected behaviour. Otherwise it is Needs Validation: it has no assertions, cannot be approved, and is only observed. Observing means sending the real requests or queries and recording the results for a human to judge.

  • Missing documentation: marked Needs Validation. This covers ordering, empty or partial city, unknown parameters, trailing slash, 404 message wording, response-time threshold, invalid token, numeric ranges (no CHECK constraints in the DB), phone format, and the total-earnings invariant.
  • Conflicting evidence: recorded, not resolved by picking a side. Examples: the contract's date-time (RFC 3339 requires an offset) versus offset-less DATETIME values (TC-LST-030), and the documented SQLite versus the connected MariaDB.
  • Partly established expectations: only the established part is asserted. For the city filter, "every DB streamer in that city is returned" and "no unrelated city is returned" are asserted; exact-vs-substring matching is not assumed.
  • Derived expectations (API↔DB field equality, relationships, audit-log replay, contract↔schema consistency) are marked defectBasis: derived. A reproducible failure of one of these becomes a suspected defect that needs human confirmation, never a confirmed one.

Resolving a Needs Validation case (dashboard → Execution Summary → Needs Validation)

  1. Run it and see the actual result. Observe now sends the real requests and queries and shows what actually happens, with no pass/fail.
  2. Choose the expected behaviour and check it. Each case offers concrete options, such as "unknown parameters are ignored" vs "rejected with 422", a response-time threshold in ms, or a phone regular expression. Each option has its own assertion. Check now runs that assertion once against the live API/DB and shows expected vs actual with Pass/Fail. This is a preview only; it is not recorded as an automation run.
  3. Save it as a requirement. The decision is stored in data/validations.json with its date and the reviewer's comment. The case becomes executable with defectBasis: requirement, and the decision appears first in its evidence list. Because the definition changed, the case returns to Pending Review. Once approved, Start Automation records the official Pass/Fail with retries, logs and bug reporting. A failure reproduced in all 4 attempts is a confirmed defect against the reviewer's requirement. Clear requirement returns the case to Needs Validation.

7.6 Assertion and database validation

CategoryWhat is compared
Status / media type / schemaHTTP status against the contract (200/404/422). Content-Type against application/json. Body against StreamerOut, ErrorResponse or HTTPValidationError from the live contract.
Counts and boundariesArray length against min(limit, SELECT COUNT(*) FROM streamers). An empty array is expected beyond the last row.
FiltersAPI result sets against DB rows: status and tier against streamers columns, and city against locations.city joined through the declared FK. AND-combination and pagination inside a filter are also checked.
PaginationThe union of small pages against the DB ID set: no duplicates, no gaps, and each page within its limit.
API ↔ DB rows
  • Rows matched: ID sets are compared both ways (TC-DB-002).
  • Field mapping: each API field maps to the column with the identical name in information_schema. location.id maps to location_id only because the FK is declared. Unmapped fields are listed, not asserted.
  • Value comparison follows the column type: FLOAT with single-precision relative tolerance (1e-6), INT numerically, DATETIME as a normalised local timestamp, and VARCHAR/ENUM as exact strings.
  • Coverage: both the collection endpoint (TC-DB-003) and the detail endpoint for every DB ID (TC-DB-014) are checked.
RelationshipsThe embedded location is compared with the locations row referenced by the FK (TC-DB-004). Every earnings.streamer_id must resolve through the detail endpoint (TC-DB-005).
Write historyFrom the full audit_log:
  • Streamers whose latest event is DELETE must be absent from the table and the API, and the most recent 5 must return 404.
  • Streamers whose latest event is CREATE, UPDATE or PATCH must be present.
  • The latest change values must equal the current API values.
Contract ↔ schemaContract TierEnum and StatusEnum must equal the DB ENUM definitions. Contract types and nullability must agree with the column definitions (TC-DB-012/013).
SecurityThe contract declares no security requirement, and both endpoints return 200 without credentials. An SQL-like ID is treated as a literal (404, no data).

Avoiding false positives:

  • Nothing is asserted about undocumented ordering, message text, extra fields or timing.
  • Non-existence is proven in the DB before a 404 is expected.
  • Numeric tolerance is used only where the column type is FLOAT.
  • Data is re-read from the API and the DB on every retry, which absorbs concurrent changes on this shared system.
  • An attempt with no assertions is never reported as passed.

7.7 Test case generation and approval

Where scenarios come from:

  • Everything the Swagger contract defines for the two endpoints: boundaries, types, every enum value, the documented filter semantics, and both error responses.
  • Cross-endpoint identity between the collection and detail endpoints.
  • What the database schema makes checkable: row sets, declared FKs, ENUM and type definitions, and write history.

Avoiding duplicates: each case checks one distinct behaviour. Multiple values of the same behaviour (for example, every enum value) are grouped into a single case.

IDs: cases are numbered TC-<area>-NNN, where the area is LST, GET, XEP, DB or SEC.

Approval control:

  • Every case starts as Pending Review. Nothing is auto-approved.
  • Only cases that are executable and approved, with an unchanged definition hash, are executed.
  • Rejected cases are excluded. Needs Validation cases are refused by the approval endpoint.
  • Start Automation is disabled until at least one eligible case is approved, and the server re-checks this when a run is started.

7.8 Execution, retries and failure analysis

  1. Start: the server snapshots the approved executable IDs. A second start while a run is active is refused with HTTP 409.
  2. Preparation: fresh API discovery and DB schema discovery. If the DB is unreachable, DB-dependent cases are Blocked with the exact connection error.
  3. Execution: 2 workers process the approved cases. One shared limiter gates every HTTP request and every SQL query (cases, retries, discovery, observations), so there are at most 2 operations in any 1-second window. This means the DB never receives more than 2 queries per second from the framework. The report shows the HTTP and DB counts separately, along with the maximum observed per second.
  4. Attempt outcomes: each attempt ends in one of these:
    • passed;
    • assertion failure;
    • connectivity error (HTTP, or a dropped DB/SSH connection);
    • dependency unavailable;
    • blocked (missing DB configuration, missing table or FK, no usable data);
    • test-framework error.
  5. Retries: assertion failures, connectivity errors and dependency errors are retried up to 3 times (4 attempts in total), with fresh API and DB data each time. Blocked cases and framework errors are not retried. Every attempt is stored.
  6. Final status: exactly one of Passed (intermittent passes keep their history), Failed, Blocked, or Not Executed.
  7. Stop: no new case or retry starts. In-flight read-only operations finish and are recorded. The run ends as stopped and is marked partial.
  8. Defect verification:
    • Confirmed defect: the same assertion fails in all 4 attempts, and the expectation comes from the contract or the documentation.
    • Unverified suspicion: everything else, including derived expectations, inconsistent failures, interrupted retries and intermittent passes.
    • Infrastructure problems never become defects.
    • Severity and priority are Unassigned — Needs Review, because no classification policy was supplied.

7.9 Reporting and traceability

The engine emits log, case and run events. They reach the dashboard over Server-Sent Events. Every case's logs record each "API request sent", "DB query sent" and "DB result received", plus the start and end of database validation, each assertion, retries, failures and the final result.

After every case, the run record is saved to data/runs/<runId>.json. Each attempt in it includes:

  • HTTP evidence: secrets redacted, phone and email masked.
  • SQL evidence: the statement, its parameters, the row count, the duration, and up to 3 sample rows with PII masked.
  • Each assertion with its expected value, actual value and source.
  • Any generated inputs.

Reference data shared between cases is attached to every case that uses it. Each defect links to its test case, endpoint, failed assertions, SQL evidence, curl reproduction steps and retry history.

7.10 Limitations

    • Documentation vs database: the Swagger description says the data lives in a SQLite file, but the connected database is MariaDB streamer_api. Its row counts and IDs match the API, so the documentation note is treated as outdated. This is recorded as a discrepancy, not resolved by assumption.
    • Consistency, not correctness: API↔DB comparisons prove the two agree. They do not prove the stored business values are right.
    • users table is never read: it contains credentials.
    • Write operations are not authorised. Create, update and delete flows are not tested, and API behaviour when the database is down cannot be tested safely.
    • No API implementation source was available.
    • Needs Validation cases are waiting for human decisions, and no severity/priority policy or response-time threshold was supplied.
    • Shared live system: other users write to this API and database. Retries re-read data to reduce false failures, but cannot remove them entirely.
    • Local storage only: approvals and run history are local JSON files. The dashboard has no reviewer login and binds to 127.0.0.1.
    • Archived runs: three earlier runs executed before the MariaDB connection was added are archived in data/archive-pre-mariadb/. They are not shown in the dashboard.
